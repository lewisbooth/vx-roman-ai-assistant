# Admin console

The Roman backend is a React Router framework app with a separate embedded admin console, Tailwind CSS 4 and Shopify Polaris web components. It owns Shopify authentication, webhooks, customer conversation APIs and persistence. Customer UI belongs in [`frontend/`](../frontend/README.md).

Run all commands from the repository root. Both apps share its package manifest and lockfile.

## Backend ownership

This server and its embedded admin UI run together locally in Docker for now; the same image can run on one Azure VM later. Customer sidebar API routes also belong in this app, outside the merchant-only `/app` layout. They need their own customer/session authorization; storefront visitors do not have Shopify Admin sessions. Keep AI clients and data-access logic in server-only modules, with browser-safe request/response types shared only when needed.

Prisma's `Session` model stores Shopify authentication. Separate `Conversation` and `ConversationMessage` models store anonymous shop-scoped chat, ordered messages, completion state and actual model/service tier. SQLite lives in the Docker volume, independently of the image. Transcripts survive app uninstall; authorization stops when the offline installation or required scope is removed.

## Text conversations

`prompts/knowledge-base/upsell.ts` is the first code-managed knowledge module, composed into the shared backend advisor prompt for text replies and voice briefings. It covers total blackout, motorization, no-drill families and guarantees as opportunities to investigate, with current availability, compatibility and price supplied by store tools. Add future product/support knowledge as focused modules here; avoid copying business rules into each channel's prompt.

Text chat connects `gpt-6-luna` through the Responses API with `service_tier: "fast"`, medium reasoning and `store: false`. OpenAI currently reports Fast responses as `priority`; the actual returned tier is persisted. Set `OPENAI_API_KEY` in the private root `.env`. Docker must be recreated after environment changes. Roman's database is the conversation source of truth; provider conversation IDs are not used. A `403 model_not_found` request rejection is retried once, before any model output or storefront action; continued rejection fails explicitly and has no model fallback. If a provider response ends with `max_messages` after a completed tool round, the runner allows one terminal-question repair using the confirmed results. This shares the existing reply-repair budget, cannot dispatch storefront actions, and never uses incomplete output. Other failures remain explicit; logs retain only safe provider status/reason/code categories.

[`prompts/shared.server.ts`](prompts/shared.server.ts) owns Roman's character, welcome and shared backend business/tool rules. [`prompts/text.server.ts`](prompts/text.server.ts) adds text greetings and Markdown presentation. Product choices use carousel buttons or conversation input, without product/PDF links in the transcript. [`prompts/voice.server.ts`](prompts/voice.server.ts) owns GPT-Live's speech, delegation and opening instructions, plus the backend's separate factual voice-briefing format. The voice backend uses the shared rules without inheriting text greetings or Markdown instructions. `ROMAN_PREAMBLE` supplies the generic voice/text welcome: "Hi! I'm Roman. Where would you like to begin?" A specific initial request or quick start retains "Hi! I'm Roman, your digital shop-at-home advisor." and a relevant next step instead of the generic menu. Resumed conversations pick up the customer's topic without another introduction. The frontend renders text safely; the database retains the original text. Prompt changes require rebuilding the backend container and restarting any active voice connection. The generic welcome uses one canonical question with Help me measure / Explore products / Find my style answers. Text calls `ask_question`; its canonical question appears in both the transcript and active answer panel, with only one transcript copy after answering. A genuinely new voice conversation saves the same question once at the provider/browser-ready gate, with no extra model call or speech cue; existing requests, previous conversations and early customer speech suppress that generic menu.

The first message bootstraps through Shopify's signed `/apps/roman/bootstrap` proxy. It requires an installed offline session and approved `write_app_proxy` scope. Root `shared/storefronts.ts` maps the two enabled permanent shop identities to exact storefront origins, including `https://shopify-single-dev.hdecom.com`. The browser includes `storefront_origin` in the proxy query; after signature verification it must belong to the authenticated shop and match any Origin header. Subsequent requests require a random conversation bearer and that conversation's exact saved origin. Credentials expire after seven days and stay in tab-scoped storage. Changing storefront domains starts fresh browser state; historical sessions remain in admin. CORS does not replace authorization, and localhost has no bypass.

Generation continues if the browser disconnects. Request UUIDs deduplicate submissions; a restart marks unfinished replies failed instead of replaying them. The browser polls partial snapshots while a reply is pending because Cloudflare Quick Tunnels do not support SSE. Limits are 4 concurrent replies, 90 seconds per reply, 4,000 input characters, 40 turns per conversation, 20 new conversations per shop per 10 minutes and 100 per day. These are development bounds, not a production abuse-control service.

Successful Roman product navigation in the current conversation establishes the active blind, independently of manual page observations; ending chat unloads it. The product remains visible in Roman while customers measure and configure by voice or text. Catalog carousels replace collection browsing. The shared shopping-interface prompt applies to text, voice briefings and live speech; `show_view({view: "chat" | "cart" | "gallery"})` changes Roman's visible tab when requested, independently of background `navigate`. Cart display never follows an addition or internal cart read. Gallery is an empty home for future customer photos/visualizations; uploads and generation are unavailable. Recommendations first establish the room and main requirements through one useful quick question at a time, reusing supplied details. Category choices reflect the opening, access and whole-opening versus individual-pane intent, rather than a fixed roller/Venetian menu. Colour and motorization variants do not count as different families; fewer suitable choices are preferable to padding. Direct product choices, configuration and more-results requests within unfinished discovery do not restart intake. Sample additions are side tasks: confirmed additions and already-in-cart results resume any unfinished measuring or configuration question, with its relevant quick answers. Keep Shopping after a sample continues that task, even when an older full-product addition exists; an explicit new goal still takes precedence. With no unfinished task, Roman offers contextual next actions. After a confirmed full-product addition, open-ended Find more products / Keep Shopping starts fresh discovery with the next room/window and requirements before catalog recommendations; prior product-specific filters do not carry over unless the customer makes them relevant. Explicit same-room requests and already-supplied next-goal details avoid repeated questions. This scope rule is shared by text, voice briefings and Live speech; saved history, cart and active-product display remain intact. Roman checks candidate descriptions and known fitting constraints before endorsing products, using batched lookups or relevant original guidance only when needed. The server-local `show_products` tool selects up to ten current-turn verified IDs without consuming a storefront call; cards retain those IDs and hydrate current details. Each card sends a structured product choice in text or voice, displayed as `I'd like the <product title>.` Exact product, carousel and path references remain attached for verification. Quick answers refine browsing, while explicit replacement confirmation takes priority; the terminal reply tools own those questions.

Opening on a PDP retains the welcome tiles. The quick answer is Something else; selecting the card establishes the active blind through normal navigation. Declining starts room/requirements discovery and does not repeatedly offer the background product. An explicit product choice or a clear request for alternatives skips this clarification.

Sources are restricted to the conversation-origin `/cdn/shop/files/` or exact Shopify file-CDN paths. `guides/session.server.ts` reuses originals for the same conversation and uninterrupted product visit for up to 30 minutes (16 sessions / 32 MiB). Product departure, expiry, eviction, restart or refresh invalidates reuse; ending chat clears its cache. Document-reading status ends with the next substantive provider response. Missing or mismatched sources trigger relevant library fallback, never invented guidance; irrelevant companion problems remain silent. PDFs are backend evidence, not customer widgets: no guide-display tools or inline PDF links are offered. Historical guide parts remain readable for admin inspection.

Manual page observations and Roman navigation stay quiet model/admin context in the customer UI; public journey paths exclude queries, hashes and private routes, with 200 visits per conversation. A claimed successful `navigate` persists its pathname/title event atomically; failed, cancelled or duplicate results create none. End chat stops voice, cancels work, rejects later writes and retains the transcript.

HTML diagrams/videos are not interpreted. `read_library_guides` reads selected discovered IDs on demand, never model-authored URLs. `guides/library.server.ts` caches discoveries/originals for 30 minutes (16 entries / 32 MiB); receipts remain conversation-, origin- and product-scoped. Calling `discover_guides` again recalls exact cached HTML sections on demand, without a browser fetch, PDF attachment or TTL renewal. Recall retains the original source and any selected-PDF binding. Cancelling unfinished work discards only that turn's new discoveries, preserving evidence from earlier completed turns. A library link alone does not establish suitability. HTML reads are limited to 1 MiB/ten seconds and projected results to 120 KiB. Fetched scripts, images and custom elements never run. The first matched guide gets one short introduction and its first question in the same reply; later steps reuse evidence without narrating document access.

The server-local `ask_question` and `ask_measurement` tools terminate a reply with one canonical payload: `message` contains necessary context or a confirmed outcome, `question` owns the question, and choices or measuring instructions belong in their own fields. An empty message is valid. The model completes reads, actions and carousels first, then calls one reply tool alone. No separate narration request or intermediate model prose is published. A missing or malformed terminal reply gets one bounded correction with only reply tools available; earlier actions cannot be replayed. Provider refusals remain explicit. Voice validates its complete assembled briefing against the speech limit rather than silently truncating it.

Every substantive reply offers the next useful decision, using one to four short answers, or a supported numeric reading. Original measuring/product/style capabilities are available when no contextual next step remains; the runner does not append an unrelated fallback menu. Answering by choice, text or speech retires the controls. Text renders the same structured question in the transcript and active answer panel; retiring the panel leaves one historical question. Measuring instructions and any known unit hint belong only to the active panel, leaving the short question and submitted value in customer history. The field label remains internal metadata. The durable instructions remain available to the model and admin. Voice keeps actual captions as its spoken history; retiring voice controls creates no extra message. Choosing an answer continues an active voice connection and does not imply cart approval. Admin retains the original question/options as labelled reference evidence. Model history projects these as application records rather than assistant prose examples. These rules preserve the existing measurement confirmation and cart approval boundaries.

`ask_measurement` uses that same durable question part and answer lifecycle with free-text input, product path, an internal label, nullable unit hint and optional instructions. Answers retain the customer's exact text and units; the field never appends its hint. It requires validated product-guide evidence or a verified library source bound to that product, with any diagram-dependent details read from the relevant original PDF, and shares `ask_question`'s one-question budget. The shared advisor prompt owns grounded guide use, units inferred from customer responses, individual readings, a single pair confirmation and applying to the PDP, followed by optional configuration through actual theme choices. There is no upfront unit menu. Mixed units retain the original readings; Roman clarifies conflicts and confirms a reconciled pair in one display unit before saving. Mutation tools never convert values themselves. Stopping or switching products abandons partial readings. Complete measurements supplied upfront keep the shorter confirmation path. Unrelated guide mismatches remain silent: a wrong fitting PDF does not block measuring supported by a matching measuring PDF. Model interpretation and step selection remain probabilistic; tool validation and PDP mutation checks still enforce their existing boundaries. Partial readings live in the transcript, while confirmed pairs use the existing measurement draft storage; no new table or wizard state is added.

`prompts/knowledge-base/handoff.ts` owns the limits of human support: Roman cannot connect to a live agent or open a Zendesk conversation. `get_store_support({})` reads the current footer's contact block for its phone, opening hours and contact link; verified hours are stated directly, while missing fields and present-time availability remain unknown. No hardcoded telephone or availability is used, and the tool never calls, messages or navigates.

Voice startup receives the server-selected pending question, or an explicit no-pending-question marker. Historical welcome menus are not candidates unless still current. Switching from text continues the chosen product and latest confirmed outcome without a fresh greeting or generic menu. At readiness, the server directly resumes one saved unanswered non-welcome question without a Live opening cue or a second provider delegation. Live stays silent until that verified briefing arrives; unsolicited delegations without fresh customer input do not produce repeat-request commentary. That reply can only reuse verified prior-read instructions (request originals when needed) and reissue the same question; it cannot navigate, search or mutate the storefront. The repository checks the question again before committing, and speech, answers, page changes or stopping cancel pending startup work. Other delegation still requires a fresh customer request. Numeric briefings include the instructions as well as the question.

All successful reply tools finish directly from the validated call, including ordinary questions, numeric steps and saved-question resumes. Their message preserves confirmed action outcomes without another completion request. The same Luna, Fast-tier and medium-reasoning configuration serves text and voice briefings. `guides/context.server.ts` places explicitly requested original PDFs in deterministic user-role reference messages before changing history and tool receipts. Explicit 30-minute [provider cache breakpoints](https://developers.openai.com/api/docs/guides/prompt-caching) cover the stable instruction prefix and each unique document; the changing conversation has no cache-write marker. The cached document prefix contains source URLs/versions and content hashes; current product binding is separate, so the same exact PDF can be reused across products without implying it suits each one. The store/mode routing key remains stable with and without PDFs. Tool schemas stay fixed and `allowed_tools` narrows each round without changing runtime budgets. No generated summary replaces the sources. Reuse deliberately accepts unchanged guides during the bounded session lifetime; document suitability is still assessed from their contents. Historical widget provenance is accepted only with the server cache receipt, completed same-conversation source, matching product and no intervening departure. Cache hits reduce repeated input processing, not reasoning; inspect actual cache-read/write usage in the dashboard to measure savings. The first cache write still has a charge. Library originals use the same explicit cache policy: deterministic URL order precedes changing history, and identical URL/bytes reached through both PDP and library attach only once while retaining both source references. Hits depend on matching prefixes and the provider cache lifetime; they are measured per request, not attributed to individual PDFs.

Cart and measurement tools share the text runner used by voice delegation. `get_cart` reads the current storefront basket. On the shopper's explicit add request, Roman silently reads the current supported native configuration and settled quote, then `add_to_cart` uses an ordinary one-use claim to submit the valid chosen product without a conversational recap, reconfirmation or approval panel. Missing/invalid configuration, unsupported required controls, unresolved fitting concerns and unconsented paid choices remain blockers; the theme still owns validation. `remove_from_cart`, `set_cart_quantity` and `clear_cart` still require explicit browser approval before their one-use claim. `apply_measurements` uses an ordinary one-use claim after one conversational confirmation of the width, drop and units; it has no extra approval panel. Required cart approval is transport state, never a model argument. Cart writes remain limited to one per reply and cannot share a reply with form changes. A form sequence permits up to three option changes and one measurement application on the same product, using fresh configuration capabilities between changes; an unconfirmed result stops further writes. Measurement or option changes are followed by a fresh configuration read and, at a natural flow completion, a compact summary with Add product / Keep configuring / available sample choices. This summary is not a prerequisite for an explicit add request; selection or measurement confirmation alone still does not request an addition. Applying dimensions alone never allows an immediate add in the same reply. `add_sample_to_cart` uses the PDP?s separate sample control on explicit request, without requiring blind dimensions or a guarantee offer. After a confirmed addition or an already-present sample, Roman continues a requested next task or offers contextual quick answers such as finding more products, measuring another window or viewing the cart, while preserving saved work; preferences apply only to the relevant discovery goal. `get_product_configuration` reads supported native choices; `configure_product` applies one available option from that fresh read. Roman can map established intent and the measuring method to native choices without asking again: outside-recess fitting to Exact, then a fresh read to select Bracket to Bracket for a full-width reading. The PDF need not use the PDP labels. Dimensions stay unchanged; ambiguous preferences still need a question. Each option change waits for the native update before another read. Same-snapshot parent-option references identify nested choices; Roman compares newly available choices, resolves established intent or suitable defaults, and asks only about meaningful unresolved preferences. Optional `priceLabel` values disclose native option surcharges in those questions, separately from the brief `configuredPrice` product total in a fresh completion summary. Missing or stale prices are not guessed. These fields remain absent in historical results. A native control with `purpose: measurement_guarantee` is offered during guided product configuration, unless the customer already accepted or declined its unchanged guarantee terms and fee for this product and window. A direct add request is not interrupted to offer an unselected guarantee. A selected paid guarantee still requires consent before adding. Roman quotes its native description and separate fee, and selects it only after an explicit customer answer; defaults, measurement confirmation and product-add approval are not opt-in. The supported PDP's configured price excludes this guarantee, so Roman reports the amounts separately without summing them. Cart-level insurance remains outside these tools. Completion retains contextual quick answers; neither tool chooses arbitrary preferences or bypasses unavailable controls. Sanitized outcomes persist for later turns; an interrupted or unconfirmed submission must be checked rather than replayed. Catalog matches do not establish fitting suitability, stock or a configured quote. A confirmed full-product addition completes that blind's configuration task. An ambiguous request to measure another window gets a same-blind-or-different clarification, except once fresh discovery has begun; the still-open PDP is not a new selection. History, drafts and reusable original guides remain available, but previous dimensions, fit conclusions and purchase/guarantee consent do not authorize another window. Photo uploads and visualization remain later work.

Checkout requests use the strict `open_checkout {}` browser tool: one claimed attempt opens only this storefront's `/checkout` in a separate tab, leaving Roman and its cart intact. The result distinguishes a requested new-tab navigation from a blocked popup; a blocked customer uses **Continue to checkout** in Roman's Cart. Neither outcome confirms checkout loaded, payment or an order. `prompts/knowledge-base/checkout.ts` owns the shared handoff policy; after a verified result the backend returns one brief sign-off with further tools disabled, without another question widget. Voice startup resumption cannot invoke checkout.

A theme-confirmed `added` result includes `addedProduct: {productPath, title, measurements?: {width, height, unit}}` when its submitted product identity is available. Measurements come from the actual submitted product configuration, with `unit` in `mm`, `cm` or `in`; they are omitted when unavailable. With that product identity, the repository persists a `cart_added` context notification with the confirmed tool outcome, independently of whether the model finishes its reply. Repeated result delivery must not duplicate that notification. Both text and voice timelines retain the event, and the customer UI presents it as a centered plain-text event, naming the product and showing submitted width/drop/units when present. A confirmed sample instead includes `addedSample: {productPath, title}` and persists a distinct `cart_sample_added` event; an already-present sample creates no new addition event. These notifications confirm the addition, not checkout or payment.

`measurements/` owns product-scoped drafts and idempotent writes. Authenticated `POST /api/conversations/:id/measurements` accepts `{requestId, name, arguments}` for manual get/set; model calls use the same service. Drafts preserve width, drop, units, window/order meaning and mounting without conversion or deductions. Limits are 20 products and 200 manual request receipts per conversation. An old request returns its original result without overwriting newer values. Ended conversations reject writes. For a configure/fill request, Roman confirms the pair once with **That's correct** and **Change measurements** quick answers, then saves and applies the confirmed values. A change asks for revised values before another confirmation. It does not ask a separate finished-dimension or mounting questionnaire. `order` means values confirmed for entry into product inputs; it does not establish manufactured dimensions or fitting suitability. Applying dimensions freezes and revalidates the saved draft at claim time, then checks the current product, units and fields immediately before editing.

The [frontend tool drawer](../frontend/README.md#developer-tools) executes public catalog calls and browser-owned cart/navigation actions directly. Catalog, navigation and cart actions need no admin server; persistent measurement tools use the authenticated conversation service. Keep browser actions at their current owner and return their results to the conversation runner.

`guides/files.server.ts` downloads only product or library PDF links verified by the browser tools, on the conversation origin or exact Shopify file CDN host, without cookies or redirects. Reads have a 10-second deadline and 4 MiB file limit; each read selects at most two PDFs, and a fallback reply attaches at most three distinct originals (for example a PDP guide and two relevant bay guides). A 15-minute memory cache holds at most 16 files / 32 MiB by exact URL and version. PDF bytes never enter SQLite, browser snapshots or logs. Files are attached at high detail to the existing Responses loop, so normal usage/cost reporting includes PDF input tokens; no second extraction model, vector database or Files API upload is involved. The frontend prioritizes the current main-product guide accordions over separate legacy product-accordions controls. A page-linked PDF is not automatically appropriate: when its product family or fitting system differs, Roman must say what it read and explain the mismatch, without claiming the download failed or continuing unsupported instructions. Measuring follow-ups stay with the measuring document that introduced the clearance/handle/upgrade condition; a companion is read only for a specific missing fact, and an unrelated mismatch cannot invalidate sufficient matching evidence. Measuring guidance reads the relevant tips and exceptions before asking for width/drop, using short adaptive questions for physical-fit checks such as handles, clearance, upgrades and uneven recesses. Clearance remains advisory even without a PDP depth field; only the guide supplies thresholds and allowances. Voice retains the same conditions in each concise step. Source interpretation and question selection still depend on the model; the prompts require it to stop rather than extrapolate missing guidance.

Cart results preserve Shopify's original/final totals and named line and cart-wide discount allocations through the shared validated contract. Text and voice use the same fresh evidence; absent discount metadata is unknown, not proof that no offer exists. This does not discover promotions before they apply or require additional Shopify scopes.

## Voice conversations

`voice/provider.server.ts` creates native [GPT-Live-1 sessions](https://developers.openai.com/api/docs/guides/live) with `store: false`, WebRTC and client delegation. It uses the same private `OPENAI_API_KEY` as the text advisor. OpenAI hosts both models; Docker needs no GPU or model weights. Browser audio goes directly to OpenAI. A trusted server sideband receives captions and delegation events; browser requests cannot upload captions or invoke model tools through that connection.

Roman defaults to Live's `marin` voice, retaining its natural accent and character with lively, warm delivery at a natural conversational pace. The **Developer tools > Voice** selector lists all 22 [built-in voices](https://developers.openai.com/api/reference/typescript/resources/live#built-in-voice); `shared/voice.ts` owns the validated list and default. Other choices retain their natural voice character with the same lively delivery. Selection applies to a new connection; GPT-Live-1 remains the model. Tone, pace and opening policy belong in the [voice prompt](prompts/voice.server.ts), with welcome copy in the [shared prompt](prompts/shared.server.ts). Voice and prompt choices do not guarantee an accent or exact playback: verify them by listening.

Authenticated `POST /api/conversations/:id/voice/:voiceId/answers` accepts `{clientId, requestId, text}` for typed/tile input, `{clientId, requestId, questionId, answer}` for the current saved question or `{clientId, requestId, carouselId, productId, title, productPath}` for a product in a completed saved carousel. All require this tab's active voice ownership. A product choice's bounded label and canonical path are customer reference data; the model must verify the product and apply normal replacement confirmation before acting. The selection is saved as ordinary customer text with voice, question or product provenance, then sent directly through the same backend advisor runner used for spoken delegations. Live receives a bounded silent `thinking.append` mirror and the completed factual briefing through `commentary.append`; it is never asked to rediscover the need for backend work from a generic continuation cue. Voice stays connected; no caption or duplicate written reply is fabricated. HTTP acknowledges accepted input without waiting for the model and tools; the durable pending turn drives activity and widgets. Durable receipts deduplicate retries, including after voice ends, and never replay provider delivery. Unconfirmed delivery returns 503 while preserving the selected input; the browser rereads its receipt. All UI input kinds share a limit of 40 submissions per conversation. Provider acknowledgment confirms context acceptance, not speech or completed playback.

`shared/active-product.ts` owns the current blind for the customer UI and model context: only a completed Roman PDP navigation in the active conversation selects it. A hidden native page observation never changes that selection. The backend appends a small current selection/background-page summary to text and Live history so voice restarts retain this distinction even when older history is truncated. Ending chat clears the selection without discarding its durable transcript.

The sideband also reflects raw audio packets, which Roman discards before validating caption/control events; reflected audio has no server event ID. A rejected event logs its type and failing field without audio, transcript text or identifiers. Check Docker logs when voice creation succeeds but the connection then ends.

`voice/service.server.ts` owns connection lifetime, bounded queues, cancellation and delegation to the existing backend runner. Spoken requests require explicit provider delegation; accepted typed replies and UI choices start the same runner directly. Caption pauses do not trigger work. An explicit delegation can wait up to two seconds for its delayed caption, matched by the provider's audio timeline; unrelated later speech cannot activate it. Freshness is checked before cancellation, so duplicate delegations cannot cancel or replay valid work. A fresh spoken request can supersede earlier work through normal cancellation. The backend advisor receives the combined history and returns its final factual briefing to the voice advisor; preliminary tool-round narration is excluded. Selected cards persist inline without a duplicate text reply. Ordinary superseded voice work retires silently without a failed transcript entry or caption boundary. Unconfirmed claimed storefront actions retain a check-before-repeating warning and durable uncertainty; cancellation never replays them. Already handed-off navigation cannot be undone. Page observations quietly update voice context without fabricating customer messages.

For typed replies and clicked choices, Live alone owns a brief contextual acknowledgement when useful; routine answers can wait for the verified next step without filler. The application sends no separate progress commentary or canned phrases. New accepted input immediately supersedes old advisor work. Its untrusted quoted thinking context is sent before a fixed interruption instruction, with both acknowledgements awaited together rather than adding a serial round trip. The instruction stops the old question without greeting or redelegating the input; a newer spoken request can supersede that wait. Final commentary contains the verified result, delivered directly without repeating acknowledgement or progress. Provider context and final briefings retain bounded command queues and explicit failure handling. Verify natural acknowledgement and interruption behavior by listening; provider acceptance is not proof of speech.

`voice/repository.server.ts` owns `VoiceSession` leases and exact `VoiceTranscript` fragments. The shared caption projection merges delayed customer and assistant streams by their Live-session start times, preserving each speaker's fragment delivery order and boundaries at visible messages and connection changes. Tool completion separates customer utterances without splitting an assistant sentence; hidden page observations and navigation do not create caption boundaries. Once customer speech separates replies, a delayed delegation reservation cannot split the following acknowledgement mid-sentence. Typed messages, visible events and voice-session changes still separate captions. Same-speaker captions tolerate pauses up to three seconds; stored sequences and text remain unchanged. Customer and admin views hide `[chuckle]`, `[breath]` and orphaned leading punctuation through the shared display formatter; raw captions and model context remain exact. New voice product widgets record their connection and result-completion sequence in `partsJson`. They appear as soon as ready, then follow that response's captions, stopping at another message or speaker/connection change. The same projection serves the sidebar and admin without rewriting captions or inventing spoken text. Initial GPT-Live context is a bounded recent extract; the full persisted conversation remains available to the backend advisor. Roman never stores raw audio, and captions do not prove the customer heard every word.

Voice lifecycle entries use the existing message table: **Voice chat started** is saved once when both provider startup and browser transport readiness are confirmed, before the opening cue. **Voice chat ended** records an orderly stop or End chat; **Voice chat disconnected** records provider failure, lease expiry or restart recovery. A connection that never reached readiness has no start/end entries. These context rows retain their order across reloads, appear in customer/admin transcripts, never retire a question and are excluded from model history. If captions arrive before the readiness request, the shared display places the start before that connection's first caption without rewriting stored data. Earlier sessions are not backfilled.

Authenticated `POST /api/conversations/:id/voice` accepts `{requestId, clientId, sdp, voice?}` and returns `{voiceId, sdp}`. Omitted voice selects Marin; invalid voice names are rejected. `/heartbeat` accepts `{clientId}`. `/voice/:voiceId/ready` accepts `{clientId, input?: {requestId, text}}`; a queued welcome reply is saved before readiness, suppresses the opening greeting and continues the same voice conversation once startup is ready. `/stop` accepts `{clientId, reason?: "connection_lost"}`: a browser transport failure records **Voice chat disconnected** with a server-owned error; deliberate stops retain **Voice chat ended**. Shutdown drains final captions and preserves its first terminal outcome. SDP input is limited to 48 KiB within a 64 KiB JSON body. Every route independently checks the conversation bearer and storefront origin. Allowed preflights cache permission for ten minutes; actual requests remain authenticated and responses remain `no-store`.

Opening Roman can attempt voice once after the frontend is ready, unless the customer opted out in this tab; Start voice is the explicit retry. The browser renews an active 45-second lease every 20 seconds. Initial Live instructions already contain the first greeting or returning follow-up, selected from saved Roman replies; page observations alone do not count. Provider startup and browser `/ready` (connected WebRTC, native startup event and an attached audio track) gate one compact opening-instruction refresh, followed by at most one commentary cue after its matching acknowledgement. Returning conversations explicitly continue the latest request and outcome; new conversations use the canonical welcome. The original business prompt and history are not resent. Repeated readiness events cannot repeat either step, and customer/assistant speech, stopping or cancellation before or during the acknowledgement suppresses the cue. It never waits for `audio.play()` to resolve, which could deadlock. Acknowledgement confirms acceptance, not exact words or completed playback; test the spoken continuation live. Startup projects model history and UI context from one transcript read. Browser and server debug summaries separate startup stages without audio, transcripts or identifiers.

Limits are four live connections per server, ten connections and 1,200 caption fragments / 60,000 caption characters per conversation, and ten minutes per connection. Stop drains final captions before switching to text. A lost browser, expired lease or server restart ends the connection; restoring chat never reopens the microphone. Native audio persists through successful in-place navigation, but a full reload requires **Start voice** again. The sidebar exposes mute/stop controls while collapsed.

## Conversation inspection and usage

Open Roman in Shopify admin for the current store's conversation list, counts and recorded usage. The list shows 25 sessions per page, newest first; open one for its ordered text/voice transcript, page visits, saved product references, tool outcomes and model/voice activity. **Refresh** reads the latest saved state. Product references are historical IDs, not cached catalog details. The existing theme-embed setup link remains on the overview.

`insights/` owns the read models and admin presentation. Both `/app` and `/app/conversations/:id` authenticate their own loaders and scope every query to `session.shop`; responses use `Cache-Control: no-store`. Inspection reuses the canonical conversation timeline and never ends voice, recovers a pending turn or replays tools. Credentials, provider identifiers, claim tokens and raw tool arguments are excluded from the admin read models.

`usage/` owns provider usage contracts and persistence. Each Responses request, including tool-loop rounds and voice delegation, gets one durable `ModelUsage` attempt before the API call. Terminal provider counts replace that attempt once, independently of whether the conversation was cancelled or ended. Input/output/total tokens and available cached-input, cache-write and reasoning subsets come from the provider. Final GPT-Live cumulative seconds are saved on `VoiceSession`; intermediate updates are not added together. Usage migrations preserve existing sessions and leave their unknown counts null.

Totals cover recorded usage only. Missing reports, unfinished calls and older sessions are shown explicitly; zero means a reported zero. A process crash can leave an attempt pending without final counts. Rebuild/recreate Docker to deploy this console and its migrations; these backend-only changes do not require a Shopify extension release.

### Model pricing

The overview shows this store's estimated USD cost and read-only rate history; each conversation shows its combined estimate and per-call costs. [`pricing/rates.server.ts`](pricing/rates.server.ts) is the versioned rate configuration. Periods use UTC timestamps: `effectiveFrom` is inclusive, `effectiveTo` is exclusive, and `null` leaves the end open. Startup validation rejects overlapping periods for the same model and service tier. GPT-5.6 Luna and Live rates start on 15 September 2026; Terra rates were verified and added from 16 September 2026; GPT-6 Luna Standard and Fast rates start on 23 September 2026; this is not a claim about when OpenAI introduced them. Earlier dates remain unpriced.

For a price change, close the existing period at the change timestamp and append a new entry with a unique ID, that same `effectiveFrom`, updated prices, source URL and verification timestamp. Preserve earlier rates. Commit, check and rebuild Docker to publish the change; no database editor or automatic price scraping is involved. Future periods can be added in advance.

`pricing/estimate.server.ts` chooses the rate using each request's recorded model, returned service tier and start time. `fast` and `priority` select Fast rates; `default` selects Standard. Input above the configured long-context threshold uses the higher rates for the entire request. Ordinary input is `input − cached − cache writes`; each category has its own per-million rate, and output already includes reasoning. GPT-Live uses reported cumulative seconds × the per-minute rate ÷ 60. A voice connection spanning a price change uses its start-time rate for the whole connection; Roman does not have a billing split across that boundary.

Missing usage fields, unknown models/tiers and gaps in pricing history stay unpriced, with coverage counts beside partial totals. Historical missing cache-write counts are not assumed to be zero. Estimates are calculated from saved usage without rounding individual calls; rounding is for display only. They use direct API list prices and exclude taxes, discounts, regional surcharges and hosting, so they are not invoice reconciliation. Lifetime overview costs use database totals grouped by price period and per-request context band; individual usage rows are loaded only for one conversation's inspection. Overview reads do not hold an interactive transaction across the report, so totals can advance independently while customer activity continues.

## Local Docker backend

Install Docker Desktop with Linux containers and follow the [root setup](../README.md) to create `.env`. Supply the existing app's `SHOPIFY_API_KEY` and `SHOPIFY_API_SECRET`; `SCOPES` must match its configured scopes. Use `SHOPIFY_APP_URL=http://localhost:3000` for the local landing page. If port 3000 is occupied, add `ROMAN_ADMIN_PORT=3100` and use `SHOPIFY_APP_URL=http://localhost:3100`. Keep this file private; Docker excludes it from the image and Compose supplies it at runtime.

```powershell
docker compose config --quiet
docker compose build
docker compose up -d
docker compose logs -f admin
```

Open localhost on the chosen port. The production-style container binds only to `127.0.0.1` (host port 3000 by default; container port always 3000) and applies Prisma migrations at startup. Compose overrides `.env`'s development database path with `file:/data/roman.sqlite` in the durable `roman-ai-data` volume. Use one server instance with SQLite. Preserve and back up this volume; future uploaded/generated files also need persistent storage outside the container's writable layer.

After code or environment changes, run `docker compose up --build -d`. Stop with `docker compose down`; the named volume remains. Docker does not provide source hot reload in this setup.

The installed embedded app needs a configured HTTPS URL; setting `.env` alone does not change the URL Shopify opens. Connect this Docker backend with [Cloudflare Quick Tunnels](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/do-more-with-tunnels/trycloudflare/) and the chosen host port (3100 here):

```powershell
cloudflared tunnel --url http://127.0.0.1:3100 --no-autoupdate
```

Install `cloudflared` on your machine, or use this checkout's downloaded `.agents/cloudflared.exe` in that command. Keep it running; Ctrl+C stops a foreground tunnel. Its random HTTPS URL changes after restarting. Set `SHOPIFY_APP_URL` in `.env` to the returned origin, update and release the local Shopify configuration below, and recreate Docker with `docker compose up -d admin`. Both Docker and the tunnel must run while using the installed app. Shopify webhooks use the same public endpoint; this container needs no HMR tunnel.

## Native hot reload

As an alternative to Docker, stop its container and run:

```powershell
npm run setup
npm run dev:admin
```

This uses the root `.env` and its local SQLite path. Local HMR uses port 64999; a remote development URL must route WebSocket requests to the HMR port (8002 by default, configurable with `FRONTEND_PORT`). On stores eligible for Shopify CLI previews, `npm run dev` manages the tunnel and app URLs. `npm run dev -- --use-localhost` instead uses a locally trusted HTTPS proxy and updates only the selected store's dev preview; webhooks cannot reach that localhost endpoint. The CLI currently rejects `hd-dev-single` as an eligible store, so this mode does not resolve that installation's URL. See the root README for the separate storefront watcher.

Each protected loader or action must call `authenticate.admin(request)`; authentication in `routes/app.tsx` does not protect parallel route handlers. Keep credentials and privileged API calls in `.server.ts` files and use the authenticated `session.shop` as the store identifier.

## Build and Shopify configuration

```powershell
npm run check
npm run build:admin
```

The build and type check explicitly generate Prisma's client from the schema; they do not depend on npm's install hooks. The production server is `build/server/index.js`; its client assets are in `build/client/`. Publish this app to a Node.js host. Shopify's extension deployment does not host this server.

For a later Azure VM deployment, use the same Dockerfile and Compose service with a private `.env`, a public HTTPS reverse proxy to the chosen localhost port, and a persistent database volume. Transfer the database deliberately when moving hosts; a volume on the local machine does not move with the image.

Keep temporary tunnel URLs in the ignored `shopify.app.local.toml`, copied from `shopify.app.toml` on first setup. Preserve the app identity and other configuration. Set `application_url` to the same public HTTPS origin as `.env` and `auth.redirect_urls` to that origin followed by `/auth/callback`. Whenever the tunnel URL changes, update both files and release the local configuration:

```powershell
shopify app config use local
shopify app config validate --config local --json
npm run deploy -- --config local
```

`config use local` selects the default for subsequent CLI commands on this machine; passing `--config local` makes the release target explicit. This releases configuration and the storefront extension to every store with this Shopify app installed. It does not update the running admin container. Rebuild and recreate that container separately while retaining its database volume. The checked-in base configuration still has placeholder URLs; use a stable hosted origin there when deploying to Azure. Pushing source code to GitHub alone publishes neither app.
